# OUK Help Bot — Подробная техническая документация (RU)

## 1. Цель системы

`OUK Help Bot` — это Telegram-бот, который автоматизирует воронку поступления:
- первичная анкета абитуриента,
- сбор обязательных документов,
- модерация заявок ответственными сотрудниками,
- базовые юридико-приватностные требования (согласие, хранение, удаление),
- наблюдаемость и управляемость процесса (аудит, очередь, статусы).

Документация рассчитана на новых разработчиков: после прочтения можно запустить проект, понять архитектуру и безопасно вносить изменения.

---

## 2. Архитектурная схема (концептуально)

Поток:
`Telegram Update -> Handler -> Service -> Store/Infra -> Notification/Response`

Слои:
1. **UI/Transport слой** (`handlers`, `keyboards`, `states`)
2. **Доменный слой** (`services`)
3. **Инфраструктурный слой** (`utils`, файловые хранилища, Excel)
4. **Конфигурация** (`core/config.py`, `.env`)

Ключевой принцип:
- handlers максимально тонкие (оркестрация),
- логика в services,
- доступ к данным через store-сервисы,
- повторяющиеся low-level операции в utils.

## 3. Структура проекта и ответственность файлов

## 3.1 Базовая загрузка приложения

- `main.py`
  - настройка логирования,
  - startup cleanup (`cleanup_stale_pending_data`),
  - запуск polling.

- `loader.py`
  - создание `Bot`,
  - создание `Dispatcher`,
  - подключение middleware и роутеров.

- `core/config.py`
  - типизированные настройки из `.env`.

## 3.2 Обработчики Telegram

- `handlers/common.py`
  - `/start`, выбор языка, главное меню,
  - команды: `/status`, `/my_data`, `/delete_me`, `/moderation_queue`,
  - flow поддержки.

- `handlers/registration.py`
  - FSM анкеты,
  - центр модерации заявок (необработанные/обработанные),
  - одобрение/отклонение,
  - управление правами (админ).

- `handlers/documents.py`
  - FSM загрузки документов,
  - обязательное согласие на ПД перед отправкой,
  - модерация пакета документов.

## 3.3 Сервисы (бизнес-логика)

- `services/registration_store.py` — хранение анкет.
- `services/documents_store.py` — хранение пакетов документов.
- `services/access_control.py` — права и ACL.
- `services/notifier.py` — отправка уведомлений.
- `services/excel_registry.py` — синхронизация в Excel-реестр.
- `services/documents_files.py` — сохранение файлов на сервер.
- `services/status.py` — статус пользователя и очередь модерации.
- `services/data_retention.py` — очистка устаревших pending.
- `services/user_data.py` — экспорт/удаление пользовательских данных.
- `services/audit_log.py` — журнал действий.

## 3.4 Utilities

- `utils/file_utils.py` — безопасное чтение/атомарная запись JSON.
- `utils/validators.py` — валидация телефона и санитизация текста.
- `utils/privacy.py` — маскировка чувствительных данных.
- `utils/datetime_utils.py` — единый парсинг ISO-дат.
- `utils/logger.py` — конфигурация логирования.

## 4. FSM-сценарии

## 4.1 Анкета абитуриента

Состояния `Form`:
1. ФИО
2. Телефон
3. Роль
4. Кафедра/специальность
5. Курс (если нужно)
6. Группа
7. Подтверждение

Результат:
- запись попадает в `registrations.pending`,
- отправляется уведомление ответственным,
- пользователь видит подтверждение.

## 4.2 Документы

Состояния `DocumentUpload`:
1. fallback ФИО,
2. fallback телефон,
3. аттестат/диплом,
4. удостоверение,
5. фото 3x4,
6. справка 075/у,
7. сертификат ЕНТ,
8. финальное подтверждение + согласие ПД.

Результат:
- Telegram-файлы скачиваются на сервер,
- пакет сохраняется в pending,
- реестр обновляется,
- модераторам уходит карточка пакета.

## 5. Данные и модель хранения

## 5.1 `data/registrations.json`

Структура:
- `pending`: необработанные анкеты,
- `approved`: одобренные анкеты,
- `denied`: отклоненные анкеты.

Важные поля записи:
- `tg_user_id`, `fio`, `phone`, `group`, `specialty`,
- `status` (`pending|approved|denied`),
- `reviewed_by`, `reviewed_at`,
- `created_at`.

## 5.2 `data/documents_review.json`

Структура:
- `pending`,
- `approved`,
- `denied`.

Хранение пакетами по `tg_user_id` для быстрого доступа.

## 5.3 Файлы документов

Локально:
- `data/files/<tg_user_id>/<doc_name>.<ext>`

В метаданных:
- `file_id` (Telegram),
- `local_path` (серверный путь).

## 5.4 Excel-реестр

- `data/admissions_registry.xlsx`
- используется как управленческий реестр/отчет.

Важно:
- по документам сохраняется `Telegram file_id` и `server_path`,
- это позволяет другому сотруднику работать с данными после хостинга (данные не привязаны к ноутбуку разработчика).

## 6. Права и безопасность

## 6.1 Ролевая модель

Профиль пользователя в `access_control`:
- `can_notify`,
- `can_review`,
- `is_admin`,
- фильтры `groups`, `specialties`.

## 6.2 Ограничение доступа

- проверка на админа: `is_admin`,
- проверка на модерацию: `is_responsible_user`,
- проверка на доменную область: `can_review`.

## 6.3 Приватность

Реализовано:
- согласие на ПД до отправки документов,
- retention cleanup,
- `/my_data` и `/delete_me`,
- маскирование чувствительных данных в аварийных уведомлениях.

Ограничения:
- пока используется plaintext-хранение JSON/Excel/файлов.

## 7. Центр модерации регистраций

Сценарий:
1. Модератор открывает `🛂 Центр модерации`.
2. Видит вкладки:
   - `⏳ Необработанные`,
   - `✅ Обработанные`.
3. В списке компактно отображаются:
   - ФИО,
   - статус (эмодзи-индикатор),
   - группа.
4. Открытие карточки:
   - необработанные: доступно одобрение/отклонение,
   - обработанные: видно кто обработал и когда.

ACL:
- админ видит все,
- ответственный видит только заявки своей зоны ответственности,
- при пересечении зон видно, кто именно обработал заявку.

## 8. Антиспам / cooldown

`middlewares/antispam.py`:
- cooldown теперь разделен по ключу `(user_id, action)`,
- это устраняет баг, когда действие в одном разделе блокировало другие действия пользователя.

---

## 9. Callback-контракты

Ключевые callback-префиксы:
- `review_tab_` — переключение вкладки центра модерации,
- `review_page_<processed>_<page>` — пагинация,
- `review_open_<tg_user_id>` — открыть pending карточку,
- `review_done_open_<tg_user_id>` — открыть обработанную карточку,
- `review_action_<approve|deny>_<tg_user_id>` — решение.

Документы:
- `doc_consent`,
- `doc_policy_info` (fallback, когда URL политики не настроен),
- `doc_review_*`, `doc_files_*`, `doc_file_*`.

---

## 10. Политика ПД без сайта

Если сайта нет:
- `PRIVACY_POLICY_URL` можно оставить пустым,
- в интерфейсе показывается кнопка с пометкой "не настроена",
- пользователь получает alert с инструкцией.

Рекомендация:
- хранить текст политики как локальный ресурс и показывать внутри бота отдельным сообщением (следующий шаг улучшения).

## 11. Поведение после хостинга

Данные находятся на сервере, где работает бот:
- JSON: `data/*.json`,
- файлы: `data/files`,
- реестр: `data/admissions_registry.xlsx`.

Для продакшена обязательно:
1. persistent storage (volume),
2. резервное копирование,
3. ограничение прав доступа к директории `data`,
4. мониторинг размера файлов и ротация архивов.

Чеклист для разработчика:

## 13. Troubleshooting

### Бот не стартует
- проверить `.env`,
- проверить токен и обязательные ID.

### Документы не сохраняются
- проверить права записи в `data/files`,
- проверить ошибки в логах `persist_documents_locally`.

### В Excel не видно обновлений
- проверить `openpyxl`,
- убедиться, что реестр не заблокирован внешним процессом.

### Модератор не видит заявки
- проверить права `can_review`,
- проверить назначенные `groups/specialties`.

## 14. План долгосрочного развития

1. Переход на БД (`SQLite`/`PostgreSQL`) как источник истины.
2. Вынос `Excel` в формат экспорта, а не основного источника.
3. Напоминания 24/48 часов через scheduler.
4. Сценарий "нужны правки" по конкретному документу.
5. Централизованный объектный storage (S3/MinIO) для файлов.

## 15. Психологическая поддержка

Реализовано:
- анонимные тикеты (`services/support_tickets.py`),
- тикет создается при выборе раздела "Психологическая поддержка",
- сообщения пользователя уходят в чат психологов (`PSYCHOLOG_CHAT_ID`),
- ответ пользователю приходит только если психолог ответил `reply` на сообщение в чате психологов,
- есть закрытие тикета и оценка 1..10,
- ведется статистика: кто из психологов и сколько раз отвечал в тикете,
- для психологов доступны кнопки просмотра истории по тикету и по анониму.

Механика напоминаний:
- после ответа психолога пользователю назначается напоминание через 24 часа,
- фоновой цикл в `main.py` проверяет и отправляет напоминания раз в час.

Важно:
- для раздела психологической поддержки нет шага подтверждения отправки и нет cooldown на подтверждение.
